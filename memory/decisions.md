# Decisions

## Identity and sharing

- Identity is nickname plus four-digit PIN, not email/OAuth.
- PIN verification uses server-side hashing and an HttpOnly secure session cookie.
- Trips are private to members; invite codes explicitly grant access.
- Guests may read a shared trip but cannot add, vote, reorder, edit, or delete.

## Data

- Each trip owns flights, places, votes, itinerary, transports, and members.
- Flights remain one persisted record per leg. Multi-leg submissions group records with `journeyId`, `segmentIndex`, and `segmentCount`; "round trip" is still a creation mode, now with independent ordered legs in both directions. This preserves existing itinerary/map behavior and legacy records while supporting transfers.
- Itinerary items have stable IDs. Transport segments connect two adjacent item IDs and are flagged for review when reordering breaks adjacency.
- Place categories use the shared top-level groups attraction, restaurant, and lodging.
- Undo is intentionally one level. It snapshots the last reversible trip-content edit, is shown consistently on all main pages and editable sheets, and does not attempt to reverse authentication, membership, or remote invitation actions.
- Shopping data is keyed by member ID plus trip ID and is authorized server-side against current trip membership. It is deliberately excluded from shared trip state, votes, invitations, and guest views.
- Shopping prices are stored as a positive numeric amount plus an allowlisted ISO currency. AI may copy only a clearly visible single-item price from the submitted screenshot; it must not substitute a web price. Totals stay separated by currency because silent conversion would make the estimate look more precise than it is.
- Shopping screenshots and manually selected product reference images are compressed client-side and stored with private shopping records in Redis for this web prototype. A persisted `photoKind` distinguishes a manual product image from an AI recognition source screenshot so detail and edit flows keep the correct meaning. Up to 16 higher-resolution private images may be retained, subject to the existing total payload ceiling. Leaving or being removed from a trip deletes that member's private shopping record for the trip.

## Maps and external data

- Google Maps JavaScript API is the preferred interactive map; Leaflet/OpenStreetMap remains a fallback.
- Travel Area and address/administrative data are separate persisted concepts. Google structured address components are raw location evidence only and never directly determine the final grouping label. Places retain raw address components and administrative information separately from the product-level `travelAreaKey`, `travelAreaZh`, and `travelAreaLocal` fields. Collection grouping uses only the stable `travelAreaKey`; its title is always rendered as `繁體中文（當地語言）` from the paired display fields.
- Travel Area rules optimize for whether travelers would reasonably schedule places on the same day, not for a uniform administrative level. Japan may mix well-known neighborhoods, wards, and cities: 神宮前 and 神南 map to `shibuya` / `澀谷（渋谷）`, 花川戶 and 雷門 map to `asakusa` / `淺草（浅草）`, 銀座 maps to `ginza` / `銀座（銀座）`, while 練馬區 and 鎌倉市 map to `nerima` / `練馬（練馬）` and `kamakura` / `鎌倉（鎌倉）`. Korean and US rules preserve their existing travel-useful granularity, including `myeongdong` / `明洞（명동）` and `brooklyn` / `布魯克林（Brooklyn）`; they must not be widened to 中區 or紐約市. Manual Travel Area assignments always take precedence over automatic recognition.
- Automatic resolution succeeds only when a product-level Travel Area rule produces a stable key and both display names; an API response by itself is not success. A new resolution version must reprocess every older automatically resolved record, including records marked complete by versions 2 and 3, while manual assignments remain intact. A failed refresh retains the last usable Travel Area and records a retryable/manual-edit state; it must never leave a settled list permanently showing `正在辨識地區`. Legacy `planningRegion*`, `area`, and address-translation fields may be read during migration but are forbidden as collection grouping keys.
- Manual lodging/custom places use exact-address geocoding, never nearby-business text search. User-entered name, full address, category/type, photo, and explicit Travel Area are authoritative and locked against background Places enrichment until the user edits them again. When no Travel Area is specified manually, it is derived separately from the complete address. A Maps link is optional and is preserved when supplied.
- One compressed custom photo may be stored inside each shared place record, with a trip-level maximum of twelve custom-place photos. Place renames must cascade to name-keyed votes and itinerary references plus cached transport labels and map selection.
- Japanese restaurant imports persist a validated `https://tabelog.com/` URL at confirmation time using the full Google place name plus local area when no verified restaurant ID is known. Seeded restaurants with verified IDs override old search URLs with their exact Tabelog pages. The detail action uses Tabelog multilingual App's official HTTPS Universal Link at `tabelog-tourists.onelink.me/3eEh`, with `tabelog-tourists://rstdtl/{id}/top/` for exact pages or `tabelog-tourists://rstlst/` for search records encoded only as OneLink parameters. The Japanese domestic App's `tabelog-v2` scheme and direct custom-scheme navigation must not be used. `af_ios_url`, `af_android_url`, and `af_web_dp` all point to the equivalent `/tw/` HTTPS page when the multilingual App is unavailable.
- Places imports support ordinary place links and public shared-list expansion before Places enrichment.
- Coordinate-only Google Maps URLs are location evidence, not proof of a business or lodging identity. Degree-minute-second or decimal coordinates are reverse-geocoded to a readable address label; encoded coordinate strings must never become place names. Google address geocoding is attempted first. If unavailable, one user-triggered server-side Nominatim reverse lookup may be used with an identifying User-Agent, bounded timeout, no autocomplete or bulk/systematic requests, and visible OpenStreetMap attribution. The import preview shows an embedded map and full address, while a clear notice tells the user to paste the original booking-platform link when the accommodation name and reference must be retained.
- Link-assisted place import supports Instagram posts/Reels, Threads, Agoda, Booking.com, and Airbnb. AI extracts possible place mentions from untrusted public metadata, the allowlisted source URL, or one screenshot; booking-platform links are forced into the lodging category and may use web search when page metadata is unavailable. A structured `formattedAddress` exposed by a booking page is treated as source evidence and supplied directly to recognition, so omission from Open Graph text or AI output cannot discard a full postal address. A descriptor-heavy Booking title may use its final short segment as the official lodging name; the same suffix extraction is rerun against the complete AI-returned title before display or search when Booking blocks public title metadata. Room size, bathroom count, transit copy, and neighborhood descriptors never become the saved name. Google Places remains the source of truth for ordinary saved candidates. When a lodging has no independent business page but a verified full address is available, an exact address-only Places lookup may supply a coordinate candidate labeled `住宿座標`; a bounded, user-triggered OpenStreetMap forward lookup is allowed only when Google supplies no usable coordinate, with visible attribution. Null coordinates and `0,0` are never valid. If the user pastes an explicit lodging name, address, Google Maps link, and Booking link together, the confirmed map coordinate and booking reference are merged into one lodging record rather than separate candidates. A source-page Japanese postal code plus complete house number is authoritative: it overrides a conflicting AI/web result, filters mismatched nearby listings, and puts the exact address coordinate first. It is not treated as a business listing and cannot replace user confirmation. The original source URL is retained as a reference, while source images are not copied into shared place data.
- Public Instagram/Threads media is accepted only from allowlisted Meta CDN hosts. The importer reads the complete bounded public HTML, keeps Open Graph media plus main-post `t51…-15` image attachments, excludes profile/avatar `t51…-19` assets, deduplicates by media path, and caps the batch at twenty images, 2 MB per image, and 12 MB total. Images are fetched with bounded concurrency, MIME/size validation, and included together in one OpenAI recognition request; repeated views of the same store must be consolidated. Full video frames and replies still require official platform access or user-provided screenshots when the public page does not expose them.
- A single social post may expose up to twenty distinct place mentions. AI output and cleanup share the same twenty-place ceiling; Google candidate lookups are bounded to five concurrent requests so larger posts do not create an uncontrolled request burst, and one failed lookup does not discard other successful groups.
- The place-import sheet exposes only two content inputs: a compact universal link field and a directly visible screenshot/photo picker. Supplemental pasted text and redundant helper copy were removed. Recognition results own the remaining sheet height and scroll independently while confirmation actions stay fixed on iPhone.
- Social import is restricted to signed-in trip members, server-side credentials, safe allowlisted social hosts, and a per-member daily recognition limit. Login-gated or private posts fall back to a screenshot.
- If a social caption explicitly states an address while saying the formal lodging name is in a profile or pinned link, the import keeps an address-based lodging mention instead of discarding it. Only this address-plus-hidden-name case enables an OpenAI web-search cross-check; Google Places returns up to five lodging-prioritized candidates and the user still selects the final match.
- Social Google candidates are inspectable before import. Candidate details open as a nested sheet above the import form so the user's link, screenshot, scroll position, and candidate selection are preserved. Selecting inside the preview only marks that candidate; a separate final import confirmation remains required.
- Social recognition counts refer to distinct extracted places, while the review may show more Google Maps candidate rows. Candidate rows are grouped by extracted place, exactly one candidate may be selected per group, and the confirmation count reflects the number of distinct places that will actually be saved.
- Candidate source comparison reuses the existing recognition call rather than spending another AI request. AI returns attachment indexes alongside each extracted place, the pending review keeps the original caption and only the relevant public images when known, and all comparison-only text/image fields are stripped before shared place persistence.
- A social place group never requires accepting an incorrect Google candidate. `重新搜尋` operates only on that group, lets the user correct the name, branch, or address, requests up to five new Google candidates while excluding Place IDs already shown in prior rounds, and does not rerun the whole-post AI recognition. `略過不加` removes that group from the confirmation count while preserving every other pending group.
- The complete social candidate card opens its preview; only the radio control is reserved for quick selection. This avoids relying on a small name-only target on iPhone.
- Saved place details show an original-source action only when `referenceUrl` belongs to an allowlisted social or booking host, and the displayed platform name is derived from that URL instead of persisted free-form metadata. Google Maps place actions use same-context navigation to avoid the empty Safari tab left by `_blank` during iPhone Maps app handoff.
- Google Places candidate search never biases a location that AI already identified. Ambiguous mentions may use the trip center with Google's valid 50 km maximum radius, and a rejected biased request retries once without location bias.
- Airport selection uses a local city-to-airport catalog to avoid manual airport-code entry and extra API cost.
- Live location is opt-in and planning-map-only. It stays in browser memory, is never written to shared trip data, and stops when disabled, leaving the map, or closing the page.

## Delivery reliability

- Production HTML is not stored as a reusable browser response, while `app.js` and `styles.css` must revalidate. The document loads versioned asset URLs, and the running app checks the current script ETag/Last-Modified value when a long-lived tab returns to the foreground so a newer deployment can reload automatically.
- PWA link sharing uses a same-origin GET `share_target` route with bounded `title`, `text`, and `url` parameters. The client accepts only supported social/booking or Google Maps hosts, removes the share payload from browser history, holds it in session storage only until an authenticated editable trip is ready, and then invokes the existing review-and-confirm import path. Manual paste and screenshot import remain first-class fallbacks. This standards receiver must not be described as an iPhone Share Sheet feature while WebKit bug 194593 remains open; iPhone requires an iOS Shortcut, a native Share Extension, or future WebKit support.
- After an implementation is complete and its relevant checks pass, publish this project's validated deployment mirror directly to GitHub `main` so Vercel updates production. The user has granted standing project-specific authorization and does not want a separate deployment question each time; platform-enforced security confirmations may still appear.

## Fullscreen map workspace

- Fullscreen map browsing is implemented as an App-level fixed workspace rather than the browser Fullscreen API. This works consistently in iPhone Safari/PWA contexts, retains accessible HTML controls, and avoids a permission-dependent fullscreen transition.
- Desktop fullscreen uses a left rail and map grid. The rail may be collapsed; the active Google or Leaflet map must be resized afterward. At 700px and below the rail becomes an overlay drawer so it does not permanently reduce map width, and selecting a place closes it automatically.
- The rail reuses the same placeKind, map date, planning/day, and preference state as the normal map. A filter change must rerender without leaving fullscreen. Rail place selection pans and zooms the existing live map without opening a detail sheet.

## Shopping places versus Shopping checklist

- kind: shopping is a shared place category for physical stores and shopping destinations. It participates in Places, map filters, social/Google import, and itinerary selection.
- The bottom-tab Shopping checklist remains private per member and trip. Its products, recipients, completion state, and screenshots are never inferred from or synchronized with shared Shopping places.

## Mobile UI

- iPhone native form controls must have bounded grid tracks and at least 16px input text to avoid overlap and focus zoom.
- Itinerary time pills keep their established type size; width and centering are adjusted instead.
- Flight date/time controls remain side by side, with more room assigned to the date.
- Flight city/airport rows use an approximately 39/61 width split, prioritizing full airport names over the shorter city value.
- Overview flight cards keep the outbound/return marker in a dedicated far-left column; the center is reserved for route direction only, and the passenger note is a readable vertically centered row.
- Native date/time inputs remain the interactive picker, but their browser-rendered text is visually replaced by an app-rendered centered label for consistent iPhone alignment.
- Flight ticket OCR runs locally in the browser with a lazily loaded Tesseract.js worker. Images are not persisted or added to shared trip data; recognized fields always require user confirmation before saving.
- Shopping screenshot recognition uses server-side multilingual vision AI through the OpenAI Responses API rather than local OCR heuristics or Vercel AI Gateway. It uses `gpt-5.6-luna`, sends each compressed image with `detail: original`, requests strict structured output, preserves original-language brand/product names alongside Traditional Chinese meaning, extracts only image-stated benefits, and returns one main product. Requests require a signed-in trip member, are limited per member/day, use only the server-side `OPENAI_API_KEY`, set `store: false`, and never expose credentials to the browser. Every field remains editable and nothing is added until confirmation.
- Shopping deletion follows the same safety pattern as places and itinerary: left swipe reveals a confirmed single-item delete, while explicit selection mode supports confirmed batch deletion.
- A shopping item's original recognition screenshot remains private Redis data. GPT Image generation is not used. The recognition response's web-search sources are inspected for structured product images, up to three safe image candidates are materialized server-side, and only the user's selected candidate is compressed and stored with the private item.
- Shopping import must present up to three product-image candidates before confirmation. Each thumbnail opens a large, keyboard-dismissible preview where the user can switch candidates and select one. `換一批圖片` performs a dedicated web image search for the already-recognized brand and product, excludes candidate IDs seen in earlier rounds, and never reruns image generation. The search is adaptive: one primary query is sufficient when it yields three usable images; only an incomplete result triggers two concurrent official/multilingual backup queries, whose page sources are interleaved before image extraction.
- Multi-image Shopping imports accept up to twelve screenshots. Images are prepared locally in sequence to avoid an iPhone memory spike, then all prepared AI recognition requests are dispatched concurrently. Every card exposes its own semantic progress state so completed or failed work is immediately distinguishable while other requests remain active. Browser file pickers cannot enforce a native maximum count, so selections over twelve are rejected after the picker returns control to the App, before compression or API use, instead of being silently truncated.
- Selected web product images are converted to bounded JPEG data URLs for reliable iPhone Canvas support. The private Shopping save accepts up to 1.6 MB total selected-product imagery, and the client reconciles each newly added item with the server-sanitized response so stripped images cannot be mistaken for a successful save.
- Product-source links, domains, recommendation stars, and numeric recommendation indexes are intentionally removed from both Shopping API output and persisted annotations. Research sources may ground the AI request internally but never appear in the Shopping UI.
- Custom Shopping categories are created only through a `新增自訂分類` option inside category selectors and may be removed later; affected items fall back to `日常`. Reusable `買給誰` tags may also be removed, and recipient/status filters provide per-person bought and unbought views.
- Place details expose a low-emphasis destructive action at the bottom for signed-in editors. Its label adapts to attraction, restaurant, or lodging; deletion still requires confirmation, cancel returns to the same detail sheet, and guests never see the control.
- Overview prioritizes real planning completion and unresolved decisions instead of duplicating the Places and Itinerary navigation. Its percentage is weighted from outbound/return flight coverage (20%), lodging (20%), days containing itinerary items (40%), and transport coverage between scheduled items (20%); proximity to departure is never a completion input.
- Overview keeps the complete flight list and an explicit add-flight button because flights are a primary planning object rather than a summary-only metric.
- The Places list has one add-place entry point: the persistent bottom action. Swipe-delete controls remain fully hidden until a left swipe begins.
- Transport forms use progressive disclosure: mode-relevant fields appear first, while ticket-specific details remain collapsed until explicitly requested.

## Baseline sentinel semantics

K = travelAreaKey. R = travelAreaResolved. S = travelAreaResolutionStatus. A = autoTravelArea.

For K, absent/null/empty-string/false all fail Boolean completeness checks; direct catalog membership rejects them (string type guard), stringification would respectively yield undefined/null/empty/false; geometry membership fails. No runtime consumer distinguishes K absence from explicit null via hasOwn. For R, strict `=== true` accepts only true; absent/null/empty/false all mean unsuccessful or not current. API/editor truthiness likewise rejects all four. S has no enum parser: reads/copies are free strings, the migration guard explicitly rejects ambiguous; absent/null/empty/false are false in fallback `||` expressions and not equal to ambiguous. A absent/null/empty/false are all false for editor snapshot selection; spread/Object.entries copies present values, JSON preserves null/empty/false and omits absent; migration uses `!= null`, so empty/false fail its snapshot validation.

## Consumer-derived representation decision

Use optional `travelAreaCandidateKeys`, same prefixed name in `autoTravelArea`. Active and snapshot ambiguity: `travelAreaKey: ''`, `travelAreaZh: ''`, `travelAreaLocal: ''`, `travelAreaResolved: false`, `travelAreaManuallySet: false`, `travelAreaSource: 'automatic'`, `travelAreaResolutionStatus: 'ambiguous'`, version 5 and deterministic resolver name; no resolution error. No added timestamp, status alias, taxonomy field or fake primary. Snapshot uses the existing prefixed contract, not a second naming system.

Empty strings follow the existing resolver wire sentinel and overwrite stale singular values in object merges (unlike omission). null would unnecessarily introduce another type; deleting only in patches fails to clear spread predecessors. Before normal singular fallback, all active consumers must validate the discriminant. R remains **singular resolution success**: false means no singular winner, not necessarily a failed automatic attempt. `isTravelAreaResolutionCurrent`, editor status and the API early return explicitly distinguish terminal ambiguity from failure. This removes no existing R meaning; the Phase A singular validator intentionally stays false for candidate states in its frozen migration-only scope. No unresolved semantic conflict remains.

Candidate arrays require >=2 unique current catalog keys. Invalid values, duplicates (including a repeated key alongside two distinct keys), sparse arrays and split-brain states throw; no invalid set is silently deduplicated into a terminal state. Ordering uses an explicit code-point comparator with ebisu ranked immediately before daikanyama, independent of object insertion, evidence/async/render order. Resolved stored records omit the optional array; empty arrays in transition patches are removed by the normalizer. Auto snapshots undergo the same validation independently of active manual state. Cross-parent candidate sections exist only in normalized runtime output.

Inventory gate: complete; schema implementation may begin. Production dataset can remain zero ambiguous records. No production count was queried.

## Reconciliation and final consumer closure — 2026-09-13

Continuation arrived at the exact Phase B HEAD with six modified source files and the two inventory documents, no new test files and nothing staged. The matrix above records the original consumer discovery, not a claim that the interrupted WIP had already passed validation. This continuation retained the representation and completed the following:

- `PlanningGeography.normalizePlace` rejects illegal candidate sets and split-brain input at hydration, both resolver/editor ingress paths, snapshots and authenticated Trip PUT / both GET paths. Duplicate keys are rejected, superseding the interrupted draft's permissive deduplication. Valid sets are copied into deterministic order.
- `isTravelAreaResolutionCurrent` is the common completion decision. `shouldUpgradePlanningRegionResolution`, `needsPlanningRegionResolution`, the automatic batch scheduler and retry-button visibility all inherit terminal ambiguity. The mixed-section retry click additionally skips ambiguous records. Stale in-flight resolution responses cannot update a restored ambiguous/manual Place's identity.
- `ensureTravelAreaFields` validates ambiguity before audit, missing-triple fallback, planningRegion/area fallback and status assignment. `hasUsableTravelArea` remains a singular-only predicate; it no longer determines completion on its own. `travelAreaGroupKey` uses the normalized section when primary is null; geometry remains singular-only.
- `api/places.mjs` classifies saved localized OR original components and returns a valid exact canonical tie before any external lookup. This is initial classification from existing evidence; valid persisted ambiguity never enters the client resolution loop. Ordinary initial business lookup or a deliberate changed-address workflow remains separate from geography-only transitions.
- `enrichPlaceImportsFromApi` merges a complete automatic snapshot after identity enrichment, clears stale candidate/error state on unique results and preserves manual active fields. Raw tags/legacy fields retain their existing semantics. Draft manual/restore saves and final batch import retain original identity.
- `restoreAutomaticFields` validates a current automatic resolved/ambiguous snapshot. Restore preview reads persisted Place or candidate-draft evidence, cancels pending editor timer/stale sequence, and does not call session.resolve. Existing geography-only Save now also handles Restore and unchanged ambiguous Save: build the full next state, clear obsolete candidates/error, assign once, persist once, return to detail with refreshDetails=false. Missing/invalid snapshot is rejected without clearing manual state.
- Editor starts from saved identity for valid ambiguity, valid automatic snapshot or current matching canonical address. Changed/stale addresses retain existing explicit resolution behavior; a current unchanged-address rename no longer geocodes. One existing navigation assertion was updated to this intentional behavior; its test name remains unchanged.
- UI consumers `canonicalAreaChip`, `planningSectionKey/Label`, `placesScreen`, `canonicalFilterGeography`, `matchesCanonicalAreaFilter`, `placesFilterModel` and `matchesMapFilters` all consume normalized area arrays. Same-parent and cross-parent ambiguity produce one card/section, all chips, and match any candidate.
- Phase A manifest, catalog, migration implementation, fingerprints, conditional-write algorithm and safety gates remain unchanged. Current production ambiguity count was not queried or modified. No production records were used as test fixtures.
